# API Gateways in System Design Interviews w/ Ex-Meta Staff Engineer

An overview of how API gateways evolved as the standard edge layer for microservices, what they do inside, common production choices, and why they should be acknowledged briefly rather than deeply analyzed in system design interviews.

## Procedure / models distilled
- Model an API gateway as a thin edge layer that gives clients a single endpoint and routes requests to the correct backend microservice.
- Treat the gateway as a shared guard rail that centralizes cross-cutting concerns so backend teams can focus on pure business logic.
- Run every request through a four-stage pipeline: validate, run middleware, route, transform response.
- Validate requests at the edge by checking formatting, headers, and body, and reject malformed traffic before it reaches backends.
- Implement routing with a path-to-service lookup map or config that maps endpoints like `/messages` to the messaging service.
- Offload repeatable middleware such as TLS termination, OAuth token verification, rate limiting, throttling, logging, metrics, and caching to the gateway.
- Keep middleware calls fast because they execute on every request, and use external services like Redis for rate limits or a separate OAuth provider for token checks.
- Transform backend responses at the gateway to match the client-facing protocol, for example converting internal gRPC/RPC responses into JSON/REST.
- Choose between managed cloud gateways such as AWS API Gateway, Azure API Management, or a Google Cloud equivalent, and open-source options like Kong, Tyk, or Express Gateway.
- In system design interviews, place the gateway on the diagram, note it handles routing and middleware, and then move on without making it the focus.

## Failure modes named
- Over-focusing on the API gateway in a system design interview; it is an expectation in microservice designs and not the differentiating part of the system.
- Clients directly knowing and calling every microservice endpoint, creating tight coupling and complexity.
- Funneling all traffic through one microservice that forwards requests to others, which forces a full redeploy to change routing logic.
- Duplicating cross-cutting boilerplate such as authentication, rate limiting, logging, and metrics across every microservice.
- Running slow or heavy middleware on every request, or letting business logic creep into the gateway.
