# System Dynamics Model: Kaibab Deer Population

Donella Meadows introduces system dynamics modeling by walking through a simplified model of the Kaibab Plateau deer population collapse, showing how models are built from problem definition through causal loop diagrams, stock-and-flow structures, and iterative testing to understand ecological overshoot.

## Procedure / models distilled
- Treat a model as any set of simplified assumptions or abstractions about a complex system — including mental models — whose purpose is to support decisions under imperfect information.
- Define a system as a set of interconnected elements, with the boundary chosen by the purpose of the inquiry.
- Begin a System Dynamics study by describing the problem in words and identifying the real-world behavior to be explained.
- Build a reference mode: a graph of the actual or expected behavior over time that the model must be able to reproduce.
- Choose a time horizon that matches the reference mode so the model includes the relevant dynamics and excludes irrelevant ones.
- Start a causal loop diagram with a central variable you know must be in the model, then add variables and feedback links.
- Distinguish endogenous variables from exogenous variables, making more variables endogenous as understanding grows.
- Translate the causal diagram into a stock-and-flow (Dynamo) diagram with levels, rates, and constants.
- Start with the simplest model that might explain the behavior, then add complexity only when the current version fails to match reality.
- Add nonlinear relationships such as tables and thresholds when linear assumptions cannot capture observed behavior like irreversible damage.
- Test the model by comparing its output to the reference mode; matching the historical pattern is a milestone, not proof of correctness.
- Iterate: change assumptions, parameters, and policies to discover which structures produce or prevent the undesired behavior.
- Summarize and communicate lessons, and design policy interventions, only after extensive model testing and iteration.

## Failure modes named
- Getting lost in computer syntax or mathematics and forgetting to examine the assumptions and simplifications philosophically.
- Leaving out unstated assumptions, which are the hardest to catch and the most dangerous.
- Treating a successful match to the reference mode as proof that the model is right.
- Starting with an overly complex model instead of building from the simplest possible structure.
- Confusing exogenous convenience with endogenous reality, thereby hiding feedbacks inside constants.
